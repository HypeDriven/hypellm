    The HypeLLM outbound TLS helper

    tls-helper/ holds the reference outbound TLS helper: the process that turns the router's cleartext HTTP into HTTPS to a remote provider — DeepSeek, OpenAI, Anthropic, Moonshot, or any scheme=https endpoint.

    It is deliberately outside the Rust workspace, like verifier/ and agent/: not a workspace member, not built by cargo build --workspace, and not scanned by depscan as router source. Owner: the deployment's operator, who also owns its allowlist.

    Why it is a separate process

    Specification 4 draws the line:

    TLS reality: Do not implement TLS or modern cryptography ad hoc. … For outbound HTTPS, use a platform-provided audited TLS helper/sidecar with a narrow CONNECT-like API and destination allowlist.

    The router therefore ships a client — TlsHelper in crates/hypellm-net/src/helper.rs — and no TLS. Without a helper, a provider declaring scheme=https is a startup failure (Outbound). This is that helper.

    It is in the trusted computing base. It sees every prompt, completion and provider credential sent to a remote provider in plaintext, and it decides which certificates are authentic. Review it as such.

    What it does, and what it deliberately does not

    It performs no cryptography of its own. The TLS session is the standard library's ssl module — the platform's OpenSSL — against the system CA store, with CERT_REQUIRED, hostname checking against the SNI and TLS 1.2 as the floor, asserted in code rather than assumed. There is no path that disables verification and none that falls back to cleartext.

    It reads no URL, path or header: the router's HTTP is opaque bytes relayed in both directions on one thread, because an OpenSSL connection must not be read and written from two threads at once. It negotiates ALPN http/1.1, which is what the router speaks.

    What the router may tell it

    → CONNECT <host> <port> <sni>\n
← OK\n              then the socket carries the TLS session's plaintext
← ERR <code>\n      and the socket closes

    <host> is the address the router resolved and validated itself, so a DNS answer cannot change between the router's egress check and this connect. The helper honours that pin — it connects to exactly that address — and checks it again:

    • (sni, port) must be a row of the helper's allowlist. Deny by default. A compromised router cannot use the helper to reach an arbitrary TLS endpoint with the platform's trust.
    • The address must be globally routable — not private, loopback, link-local (where cloud metadata lives), shared address space, multicast or reserved, including the same addresses spelled as IPv4-mapped IPv6 — unless the row says "local": true. A row may also list prefixes the address must fall inside.
    • A name in place of an address is accepted only when it equals the SNI; the helper then resolves it once, keeps only permitted answers, and tries them in order within one connect deadline.

    Refusal codes: destination_not_allowlisted, address_not_permitted, host_mismatch, resolution_failed, malformed_request, invalid_port, invalid_sni (including the empty SNI the router sends for a destination with none), line_too_long, line_timeout, connect_failed, connect_timeout, certificate_invalid, handshake_timeout, tls_handshake_failed, busy.

    Obligations

    These are normative. A helper that does not keep them is not this helper.

    • Runs as its own unprivileged user. It refuses to start as root. In k8s/hypellm.yaml it is uid 1001 in the router's group 1000.
    • Its access control is the filesystem. The socket is created 0660; the directory holding it decides who can reach it. In the pod it is a memory-backed emptyDir mounted only by the router and the helper. Anything that can connect can ask for any allowlisted destination, so keep the directory to those two.
    • Never treats a router-supplied value as a destination it chose. The allowlist is the helper's own file; the router's request selects a row.
    • Ignores proxy environment variables, and logs that they were present so nobody believes they took effect.
    • Bounds everything: the request line (512 bytes), the time to send it, concurrent sessions (refused with busy rather than queued), connect and handshake deadlines, idle time, a session's lifetime, and the bytes buffered in each direction.
    • Logs no plaintext — a line names the SNI, port, peer address, TLS version, outcome and byte counts, never a header, body or key.

    Configuration

    A JSON file; tls-helper/tls-helper.json is the one the pod uses. Unknown keys are refused, so a misspelt limit fails rather than leaving the default in force.

    {
  "socket": "/run/hypellm-tls/tls.sock",
  "max_sessions": 64,
  "line_timeout_ms": 5000,
  "connect_timeout_ms": 10000,
  "handshake_timeout_ms": 10000,
  "idle_timeout_ms": 900000,
  "max_session_ms": 3600000,
  "buffer_bytes": 262144,
  "destinations": [
    {"sni": "api.deepseek.com", "port": 443},
    {"sni": "llm.lan.example", "port": 8443, "local": true, "prefixes": ["192.168.8.0/24"]}
  ]
}

    idle_timeout_ms is generous on purpose: a non-streaming completion can run for minutes without a byte in either direction, and the router's own deadline (default_deadline_ms) is the tighter bound. ca_file replaces the system store with one PEM file — for a private CA in front of a LAN slave, and for the tests. hypellm-tls-helper --config <file> --check validates a file without starting.

    A row with "local": true is how a LAN slave gets TLS: terminate TLS in front of it, list it here, and declare it scheme=https — the alternative to cleartext to slaves.

    Setting it up

    The pod already runs it: k8s/hypellm.yaml has a tls-helper sidecar (python:3.13-slim, pinned by digest, the script mounted read-only from tls-helper/), sharing /run/hypellm-tls with the router. It is idle until the router is told to use it.

    1. Allowlist the destination in tls-helper/tls-helper.json. The shipped file lists DeepSeek, OpenAI, Anthropic and Moonshot on 443.
    2. Point the router at the socket in docker/hypellm.conf's settings record: 
      tls_helper_socket=/run/hypellm-tls/tls.sock
    3. Declare the provider. For DeepSeek, with its API key in run/secrets/credentials/deepseek (a declared credential with no file is a startup failure): 
      credential id=deepseek description="DeepSeek API key"
provider id=deepseek family=deepseek scheme=https host=api.deepseek.com port=443 base_path=/v1 \
         credential=deepseek egress=remote
target id=deepseek:chat provider=deepseek model=deepseek-chat aliases=deepseek-chat \
       capabilities=chat operations=chat modalities=text \
       streaming=true tools=true json_mode=true \
       context=65536 max_output=8192 quality_class=7 cost=5 concurrency=8
alias id=deepseek-chat capability=chat targets=deepseek:chat \
      description="DeepSeek's hosted chat model, over the TLS helper"
      Take model, context and max_output from the provider's current model page; the figures above are placeholders that validate, not DeepSeek's limits. Listing the target in an existing alias as well makes it a fallback behind the local models.
    4. just up.

    Checking it works

    • just logs tls-helper shows helper.listening, then one session.closed (or session.refused with its code) per upstream connection.
    • A request to the new alias that fails with a refusal names the helper's code in the router's error, sanitised to [A-Za-z0-9_-].
    • python3 tls-helper/test_tls_helper.py runs the suite: offline, with a CA and certificates minted for the run by the openssl CLI and discarded after it. It covers the allowlist, certificate and hostname refusal, every non-global address class, prefixes, malformed and oversized requests, the line deadline, the session cap and slot release, the idle timeout, a byte-exact relay in both directions at once, proxy variables, and that no plaintext reaches the log.

    When it stops working

    • destination_not_allowlisted: the provider's host and port are not a row of tls-helper.json. The row is the pair; another port is another row.
    • certificate_invalid: the server's certificate did not verify for the SNI against the store in use — an expired or misissued certificate, an interception proxy, or a private CA with no ca_file.
    • address_not_permitted: the name resolved to a non-global address and the row is not local, or the address is outside the row's prefixes.
    • busy: max_sessions are open. The router pools connections, so this is sustained concurrency, not a leak — raise it or lower provider concurrency.

    The limitations that remain are in Current limitations under "Outbound TLS helper".
